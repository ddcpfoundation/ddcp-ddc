# Test Coverage Report

This report states what the program's and the command-line tool's test suites cover, and what they do not cover, with the reason for each gap. It is written for an independent security reviewer.

The program and command-line figures were measured on 2026-10-08, by running the suites and listing their tests. Every figure can be measured again with the commands in section 1. The tests are checks that the code behaves as described. They are not an audit.

Contents:

1. How the suites run
2. Counts
3. Instructions and their signers
4. Error codes
5. Adversarial tests
6. Command-line tool
7. Not covered, and why

## 1. How the suites run

### Program

```
scripts/fetch-fixture-programs.sh   # once, from the repository root
cd program
cargo build-sbf                     # writes target/deploy/ddcp_ddc.so at the repository root
cargo test                          # against the mainnet-beta build of Token-2022
DDCP_TOKEN_2022=devnet cargo test   # against the devnet build of Token-2022
cargo test -- --list                # lists every test by name without running it
```

- **Unit tests** are in `program/src`. They run on the host.
- **Integration tests** are in `program/tests`. They run in LiteSVM 0.12.0 and load the program binary that `cargo build-sbf` writes.
- **Token-2022.** Every integration test that touches a mint runs a deployed Token-2022 program, not a reimplementation of it. The two clusters run different builds, and the suite runs once against each.
  - `scripts/fetch-fixture-programs.sh` copies the binary from mainnet-beta into `program/tests/fixtures/token_2022-mainnet.so` and the binary from devnet into `program/tests/fixtures/token_2022.so`. Both files are ignored by git.
  - For each, the script records the program address, the cluster, the date, the slot and the SHA-256 in a committed record: `program/tests/fixtures/token-2022-mainnet.provenance.txt` and `program/tests/fixtures/token-2022.provenance.txt`.
  - `cargo test` loads the mainnet-beta build; `DDCP_TOKEN_2022=devnet cargo test` loads the devnet build. Any other value of `DDCP_TOKEN_2022` stops the run.
  - The harness refuses to load a binary whose SHA-256 differs from its record, or a record that names another cluster.
  - Run without arguments, the script never rewrites a record. When a cluster serves a binary other than the recorded one, it refuses for that cluster and leaves its record unchanged. `--refresh mainnet` or `--refresh devnet` fetches that cluster's current binary and rewrites its record, which is then committed.
- **Isolation.** The test VM is built without LiteSVM's default programs, so no copy of Token-2022 other than the one checked against its record can be present.

### Command-line tool

```
cd cli
npm ci
npm test        # compiles src to dist, then runs node --test over every compiled test file
```

- The suite uses the Node.js test runner on Node.js 24.
- **No network.** No test reaches a public cluster. Tests that need a cluster run against a local stand-in endpoint that serves fixture accounts captured from devnet.

## 3. Instructions and their signers

### The instructions

The program has eight instructions.

- **I-1 `initialize_mint`** creates the mint and the program's record of it (PDA-1).
- **I-4 and I-5** are the issuance pause and its release. The pause stops minting only:
  - burning works while paused (`burn_succeeds_while_paused`, `adv_burn_while_paused_allowed`);
  - so does a fee change (`update_succeeds_while_paused`);
  - so does a key rotation (`adv_rotate_while_paused`);
  - the pause belongs to one mint: pausing one leaves minting on another working (`pausing_one_mint_leaves_minting_on_another_mint_working`).
- **I-7** publishes the reserve statement. Its on-chain name is `publish_attestation` and its record is PDA-2.

| Instruction | Must sign | Success path |
|---|---|---|
| I-1 `initialize_mint` | the new mint keypair and the payer | `initialize_mint_builds_full_genesis_state` |
| I-2 `mint_tokens` | issuer and reserve | `mint_succeeds_credits_destination_and_supply` |
| I-3 `burn_tokens` | issuer and reserve; the source must be owned by PDA-5 | `burn_succeeds_debits_source_and_supply` |
| I-4 `pause_issuance` | any one of issuer, operator, reserve | `pause_by_issuer_alone`, `pause_by_operator_alone`, `pause_by_reserve_alone` |
| I-5 `resume_issuance` | issuer and reserve | `resume_by_issuer_and_reserve` |
| I-6 `update_transfer_fee` | issuer and operator | `update_succeeds_sets_fee_and_preserves_mint_state` |
| I-7 `publish_attestation` | reserve | `publish_writes_full_record_from_clock_and_signer` |
| I-8 `rotate_signer` | operator and reserve | `role_0_rotates_exactly_issuer_authority`, `role_1_rotates_exactly_operator_authority`, `role_2_rotates_exactly_reserve_authority` |

- **One key in both slots** means a single key appears in both slots of a two-signature instruction.
- **Rotated-out key** means a key used after it has been replaced by I-8.

**Order of checks.** The authority check runs before the business checks. Four tests pin this order:
- `paused_with_wrong_signer_is_unauthorized_not_mint_paused`: on I-2, a wrong signer is reported before the pause.
- `wrong_signer_with_bad_bounds_is_unauthorized_ladder_order`: on I-6, a wrong signer is reported before invalid fee bounds.
- `mint_mismatch_beats_wrong_signer_ladder_order`: on I-2 and on I-3, a token account of another mint is reported before a wrong signer, because the account data is checked first.

On I-8, a default key is refused before an invalid role (`pubkey_check_precedes_role_check_spec_order`, `adv_rotate_default_pubkey_checked_before_role`).

## 5. Adversarial tests

`program/tests/adversarial.rs` holds 138 tests, each prefixed `adv_`. They are checks, not an audit.

### How they were written

The tests were written blind. Their author was given only:
- the eight instructions, with each instruction's accounts in order and their signer and writable flags;
- the PDA seeds;
- the error codes;
- a list of cases to cover;
- a copy of the program with every comment removed.

The author was given no design rationale and no existing test, and was instructed not to read the instruction handlers. The copy contained the handlers, so the blindness rests on that instruction.

Where the description did not settle an outcome, the test asserts that the transaction fails and that the state is unchanged, and its comment says the error is not settled. Six tests are of that kind:
- `adv_init_happy_path_then_reinit_refused`
- `adv_init_pda1_preexisting`
- `adv_mint_destination_is_mint`
- `adv_mint_u64_max_then_overflow`
- `adv_burn_pda5_of_other_mint`
- `adv_burn_u64_max_exceeds_balance`

### What they cover

For every instruction where the case applies:

- **Signatures:** a missing signer; a stranger in a signer slot; one key in two slots; a key in the wrong role's slot.
- **Accounts:**
  - an account owned by the wrong program;
  - a fake Token-2022 or system program;
  - a PDA at a non-canonical bump or belonging to another mint;
  - a swapped account of the same type;
  - the same account in two slots.
- **Genesis:** re-initialization of an existing mint.
- **Amounts:** 0 and `u64::MAX`, and each fee ceiling exactly at its value (accepted) and one above (refused).
- **Pause:**
  - pausing by each role;
  - resuming needing both issuer and reserve;
  - rotation while paused;
  - burning while paused.
- **Rotation:**
  - rotation to the current key;
  - rotation to another role's key;
  - a two-step swap of keys, refused at the midpoint;
  - a rotated-out key refused afterwards.
- **Instruction data:** trailing bytes, short data, empty data and an unknown discriminator.

| Prefix | Tests |
|---|---:|
| `adv_init` (I-1) | 21 |
| `adv_mint` (I-2) | 20 |
| `adv_burn` (I-3) | 16 |
| `adv_pause` (I-4) | 15 |
| `adv_resume` (I-5) | 8 |
| `adv_fee` (I-6) | 19 |
| `adv_publish` (I-7) | 14 |
| `adv_rotate` (I-8) | 22 |
| `adv_dispatch` | 3 |

### The tests can fail

A program was built with four checks removed:
- the pause check on minting;
- the rate-ceiling check on fee changes;
- the distinct-key check on rotation;
- the authority check on pausing.

Against that program, exactly ten adversarial tests failed, and they are the ten that name those checks:
- `adv_mint_while_paused`
- `adv_fee_bps_one_above_ceiling`
- `adv_fee_zero_ceilings_refuse_one`
- `adv_pause_stranger_refused`
- `adv_pause_payer_as_authority_refused`
- `adv_rotate_issuer_old_key_refused`
- `adv_rotate_issuer_to_operator_key`
- `adv_rotate_operator_to_reserve_key`
- `adv_rotate_reserve_to_issuer_key`
- `adv_rotate_sequential_swap_refused_midway`

The set was predicted before the run. The check was run before the co-signer roles took their present names; the ten tests carry the names shown above. The altered program was never committed.

## 7. Not covered, and why

1. **I-2 to I-8 are tested against a seeded record, not one written by I-1.**
   - Their integration and adversarial tests build a mint with three extensions (Confidential Transfers, Transfer Fee, Confidential Transfer Fee) and write PDA-1 directly.
   - No test runs I-1 and then another instruction on the mint it created.
   - I-1 is tested on its own against the five-extension mint it creates.
   - Reason: the handlers read PDA-1 and the extensions they act on, which the seeded state supplies.
   - The combination is exercised on devnet, on the reference mint `9RTSRMFRCLKHLEzyKcTEypz5R45tPUctNMLir98y1iRa`. Those transactions are evidence outside the suites and are not re-run by them.
2. **The test VM is not a cluster.** LiteSVM runs with every runtime feature enabled. That is not the feature set of devnet or mainnet at any given time. Behavior that depends on a feature not yet active on a cluster is not tested here.
3. **Token-2022 is fixed at the two binaries recorded in the provenance files.**
   - The mainnet-beta build and the devnet build differ: their executable hashes, read on 2026-10-08 with `solana-verify get-program-hash`, differ. The suite runs against each.
   - A later Token-2022 upgrade on either cluster is not tested until that cluster's binary is fetched again with `--refresh` and the suite re-run against it.
4. **The suites test a local build, not the deployed binary.**
   - The suites load the program as built by `cargo build-sbf` on the machine that runs them. The program at `Bn36ThBHETRi1qBGSauPmocKRFfzFGvdvnAn7SAb1Jp` is the build of the same source in the pinned Docker image.
   - The two are built with different distributions of the Solana platform tools, which embed different file paths, so they are not byte-identical. The deployed program is compared with a build of this source in the image, as described in `BUILD_VERIFICATION.md`.
5. **Confidential transfers are proven locally, not on a cluster, in the suite.**
   - The tool's tests generate and verify the five proofs, and check the ciphertext arithmetic against the upstream library.
   - That the program and Token-2022 accept those transactions on a cluster is shown only by devnet transactions.
6. **The `state` command has no test of a successful read.** Its decoders are tested one by one (`mint-authorities`, `mint-state`, `mint-transfer-fee`, `program-upgrade-authority`, `reserve-statement`). Its failure paths are tested at the entry point (`network-failure`). A full successful read is checked by hand against devnet.
7. **No test reaches a public cluster.** Network fees, rent, compute use and the behavior of public endpoints are measured on devnet, outside the suites.
8. **Wallet compatibility and proof time on mobile devices** are measurements, not tests, and are not part of this report.
9. **Static analysis** (`cargo audit`, `npm audit`, `cargo clippy` with arithmetic and slicing lints, a Solana static analyzer) is a separate check and is not part of this report.
10. **`solana-lints` was not run.**
   - Its seven lints (crytic/solana-lints) are pinned to the Rust toolchain `nightly-2025-01-09`. Five crates the program itself is built from declare a minimum Rust version of 1.89 (`solana-address`, `solana-hash`, `solana-instruction-error`, `solana-pubkey`, `solana-system-interface`), later than that toolchain, so the lints cannot compile the program as built.
   - Each class the lints check is covered as follows. The adversarial tests are named by the part of their name they share; each count is of tests in `program/tests/adversarial.rs`. The Solana static analyzer was also run over the program and reported no issues, but its report does not show which instructions it analysed, so it is not counted as coverage of any class.
